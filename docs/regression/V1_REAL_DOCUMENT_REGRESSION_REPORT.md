# V1 真实标书回归总报告

报告日期：2026-09-02

## 1. 结论

V1真实标书回归阶段完成。6份授权业务文档共216页，加1组人工异常输入，覆盖短文本PDF、长文本PDF、图文混合PDF、纯扫描PDF、DOCX/WPS真实版式、合并单元格表格及损坏/不支持文件。

最终分析结果共35项风险，35/35页码有效；34/35具备可验证的文字高亮或OCR坐标框。剩余1项扫描件风险因模型证据与OCR文字行没有可靠匹配，系统正确选择不画框，没有制造虚假原文定位。

本阶段可以进入P3部署与安全，但不等于V1已经发布。部署前仍必须完成上传大小限制、持久化目录、CORS、鉴权、速率限制、备份恢复和秘密/依赖扫描。

## 5. 首次失败与修复记录

### 表格字段被忽略

首次表格样本分析虽返回HTTP 200，但分析结果对13个非空表格单元格为0命中，因此判定失败。

修复后：

- 提示词明确逐页检查表格、清单和合并单元格。
- 新增结构化采购清单：标的、规格/要求、数量、预算、进口产品和真实页码。
- 前端分析卡与Word报告同步展示采购清单。
- 第二次真实分析返回4项采购、20个非空字段，20/20可回溯原文。

### 损坏PDF文件锁

首次结构损坏PDF测试正确返回422，但PyMuPDF按路径解析后在Windows保留句柄，导致临时文件清理失败。

修复后PDF从内存字节流解析；损坏PDF返回422，临时文件与数据库均零残留。由此引入的额外内存占用必须在P3通过上传大小限制控制。

### DOCX错误预览

DOCX曾被直接交给PDF.js并显示加载失败。V1现采用Microsoft Word优先、WPS备用的真实版式转换；本机实际由WPS完成验证，分析页码和预览页码使用同一转换结果。

## 7. 外部服务使用说明

- 文本PDF、DOCX和表格分析使用DeepSeek；完整请求与响应未写入仓库或终端日志。
- 纯扫描PDF仅将缺少有效文字层的页面提交百度OCR，然后将识别文本交给DeepSeek。
- DOCX由本机WPS转换为PDF；本机没有Microsoft Word授权。
- 异常文件在本地预检阶段被拒绝，没有调用任何外部服务。
- 表格样本因首次真实回归发现缺陷，在修复后额外执行一次DeepSeek复验；没有把首次失败结果覆盖成“直接通过”。

## 8. 已知限制

1. 纯扫描样本有1项风险无法可靠匹配OCR行，因此无坐标框；这是保守降级而非通过项。
2. 纯扫描样本没有生成低风险项，低风险框真实颜色尚无业务样本覆盖。
3. 表格样本属于中等复杂度合并单元格，不覆盖多页密集、嵌套或大量跨页表格。
4. Word结论基于WPS实际渲染；Microsoft Word与WPS在缺失字体、旧DOC和复杂嵌入对象上可能分页不同。
5. AI引用和风险概念关键词不保证逐字等于原文，不能替代高亮词和页码验证。
6. PDF内存解析占用接近上传文件大小的额外内存，部署前必须限制单文件大小和并发上传。
7. 前端生产包仍有大chunk警告；Ant Design `List`有下一主版本移除警告。
8. TestClient存在Starlette/httpx兼容层弃用警告。
9. 当前Git工作区包含迁移遗留的旧入口删除状态及大量未跟踪成果，发布前必须审计并建立正式版本基线。
